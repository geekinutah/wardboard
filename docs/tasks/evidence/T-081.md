Resolution strategy: take main's `BoardShell.tsx` as the base and re-apply the five T-081 wiring edits (main side wins every hunk; my side re-applied on top):
1. **Imports** (main + my 3): `+PresentationStatus` (type), `useSyncClient` added to the sync import, `+PresentMode`.
2. **Hooks**: `+client = useSyncClient()`, `+settings, status` destructured from `useSync()`, `+presenting` state.
3. **Deferred settings effect** (new this round — see below): fetch `getSettings` only while presenting; re-fetch on reconnect while presenting.
4. **Derived**: `+presentTitle` / `+presentStatus` after `ready`.
5. **Header**: `+Present` button (≥44px secondary, `disabled={!ready}`) between `SettingsLink` and `ConnectionIndicator`.
6. **Render branch**: `if (presenting && ready)` early-returns `<div class="shell"><PresentMode …/></div>` in place of header+main. Round 1 used a ternary wrap with re-indent; I use the early return — **identical DOM in every state** (tests assert the same selectors), a much smaller diff against main, and it still replaces the *new* header contents (Summary button, Current bar, Settings, search, tabs) while presenting.

**Round-2 behavior change (the important one):** round 1's integration called `useSettings()` in the shell, which sends `getSettings` on every connect. Main's T-079 `start-proposal.test.tsx` asserts the shell's **exact request-id sequence** (`createProposal` must be `req-2` / `req-4`). The on-connect request shifted every id by one: **5 of its 7 tests failed** (e.g. `AssertionError: expected … "requestId": "req-4" … received "req-5"`; and the failure-path test's `rejected` reply targeted the old id so `getByRole('alert')` found nothing). I verified the root cause precisely: with main's BoardShell the file passes 7/7; with my `useSettings()` integration it fails 5/7; with the deferred fetch it passes 7/7.

Fix, mirroring the repo's existing `useBaseline` pattern (status-keyed effect): the shell fetches settings **on entering Present** and again after a reconnect while presenting (`useEffect … if (!presenting || status !== 'live') return; void client.loadSettings();`), and reads the value from the reactive sync state — `showNeedsApproval={settings?.showNeedsApproval ?? false}`, the exact value semantics of the contract's `useSettings()?.showNeedsApproval ?? false`. Non-presenting shells keep main's request sequence byte-for-byte. This is flagged as a wording deviation from design decision 5 (fetch *timing* only; value source and expression preserved) — controller/verifier should be aware.
