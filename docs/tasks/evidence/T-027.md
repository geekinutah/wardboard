## Findings:
`apps/server/src/photos/sanitize.ts:37-55`. `sanitizeJpeg` takes the marker code as the single byte after one `0xFF`, then reads a 2-byte length for every marker other than SOS. JPEG allows extra `0xFF` fill bytes before the marker code, and RST (`0xD0`–`0xD7`) and TEM (`0x01`) have no length. Marker codes `0xFF` and `0xD0` are not in the drop list, so the following real APP1 is kept inside that span.

Reproduced outside the contract fixtures:

1. Fill byte. `FF D8`, one extra `FF`, APP1 `FF E1 00 LL` with payload `Exif\0\0CANARY-FILL-GPS` (`LL < 256`), then `FF DA 00 02`, zeros through offset 57604 (`2 + 2 + 0xE100`, the length formed by `E1 00`), then `FF DA 00 02 FF D9` (57,610 bytes). A fill-aware walk of the input stops at SOS and has already recorded APP1. `sanitizePhoto` returned `{ok:true, ext:'jpg'}` with the same 57,610 bytes and the canary still present. The same walk of the output still reports APP1. `POST /api/photos` as `image/jpeg` with the base Origin returned 201 and wrote `photos/63d0efdec59d731350376593ea6dfb3ba5cf8040ffc7d6ee4df2c6b26dafe90d.jpg`, which still contains the canary and a spec-visible APP1.

2. RST0. `FF D8 FF D0` immediately before the same kind of APP1 (`CANARY-RST-GPS`), padded to 65,515 bytes so the false length `0xFFE1` lands on a later SOS. `sanitizePhoto` returned ok, output size unchanged, canary present, and a fill-aware walk still reports APP1 at byte 4.

That contradicts the task goal (strip EXIF/GPS before storage), the contract row “EXIF/GPS cannot reach storage”, and SPEC.md §9 (“Do not retain original uploads … or source contents … beyond explicitly approved import processing”). Well-framed APP1/APP13/COM segments are stripped; this path never classifies the real APP1 as APP1.

Required correction:

- After the introducer `0xFF`, skip extra `0xFF` fill bytes and use the next non-`0xFF` byte as the marker code, then apply the existing APP1/APP13/COM drop.
- Do not read a length for stand-alone markers `0x01` and `0xD0`–`0xD7`. Reject the image with `invalid_image` if one appears before SOS, or copy only the marker bytes. Do not treat the following header as that marker’s length.
- Add regression tests that fail on this candidate: the padded fill-byte APP1 above, and the RST0-before-APP1 file. If `sanitizePhoto` returns ok, the canary must be absent and a fill-aware walk must not report APP1 before SOS. Rejecting the file also satisfies the storage property. A short fill-byte buffer is not a sufficient test, because the current walker already rejects it when the false length runs past EOF.
